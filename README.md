# Evaluation Protocol

Internal HR evaluation stack behind sibling `root-proxy`.

## Runtime
- Public entrypoint: `root-proxy`
- Edge upstream: `evaluation-protocol:8080` on external Docker network `edge-net`
- Frontend: Vite + React packaged behind NGINX
- Backend: FastAPI
- State: PostgreSQL for users, sessions, OAuth transactions, DB whitelist, and organization tree data
- Auth: backend-owned Microsoft OAuth redirect flow with `HttpOnly` `s1` cookie sessions

## Active Scope
- Microsoft OAuth login through backend-owned transaction state
- env initialization account and DB whitelist enforcement before user creation
- `user/admin` system role
- user whitelist administration
- organization tree administration under seeded `NEXTIN`
- multiple leaders and multi-department membership support through organization memberships
- hourly cleanup for expired/revoked sessions and stale/completed OAuth transactions

## In Repo
- `frontend/`: Vite + React frontend packaged behind NGINX
- `backend/`: FastAPI backend
- `deploy/`: container deployment files for this stack
- `docs/`: database operations and maintenance notes

## Runtime Entry Points
- All real runtime and deploy flows are defined from `deploy/`.
- Shared base compose: `deploy/docker-compose.yml`
- Server runtime: `deploy/docker-compose.server.yml` with repo-root `.env`
- Local runtime: `deploy/docker-compose.local.yml` with repo-root `.env.local`
- The server and local flows differ only by the compose override and env file. Do not introduce separate non-Compose startup paths outside `deploy/README-SERVER.md` and `deploy/README-LOCAL.md`.

## Required Setup
1. Copy `.env.example` to `.env`.
2. Copy or create `.env.local` for localhost development.
3. Set PostgreSQL credentials in each env file.
4. Set the server Microsoft Entra app values in `.env`.
5. Set the local Microsoft Entra app values in `.env.local`.
6. Keep `MICROSOFT_REDIRECT_PATH=/api/v1/auth/callback/microsoft`.
7. Keep `MICROSOFT_SCOPES=["openid","email","User.Read"]`; Microsoft requires `openid`, and `User.Read` lets the backend read `/me` when the email claim is absent.
8. Set `INITIALIZATION_EMAIL` to the single bootstrap admin account.
9. Use `deploy/README-SERVER.md` for server startup and `deploy/README-LOCAL.md` for localhost startup.

## Local IDE Setup
- This section is only for editor support and local code navigation. Runtime, verification, and tests are Docker-only.
- Do not install local PostgreSQL. Use the Compose stack from `deploy/`.
- Keep these disposable local helper artifacts only when you want fast IDE resolution:
  - `frontend/node_modules`: local frontend dependency tree for TypeScript, Vite, and `npm` checks
  - `frontend/dist`: disposable output generated by `npm run build`
  - `backend/.venv`: lightweight Python interpreter and packages for IDE resolution and compile checks
- If those artifacts are missing and you intentionally want local IDE indexing, recreate them with:

```powershell
cd backend
py -3.13 -m venv .venv
.venv\Scripts\python -m pip install --upgrade pip
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m compileall app
cd ..\frontend
npm install
npm run typecheck
npm run build
```

- That command sequence recreates `backend/.venv`, `frontend/node_modules`, and `frontend/dist` from a missing-artifact state.
- Do not use local `npm run build`, `npm run typecheck`, `python -m compileall`, local dev servers, or local PostgreSQL as validation gates.
- In IntelliJ IDEA:
  - set the Python SDK to `backend/.venv/Scripts/python.exe`
  - mark `backend/` as a Sources Root if `from app...` imports still show unresolved
  - keep the frontend Node interpreter pointed at a local Node installation
  - let the IDE use `frontend/package.json`, `frontend/node_modules`, and `frontend/tsconfig.json`

## Verification
- Run verification only through Docker Compose from `deploy/`.
- Local runtime is documented in [deploy/README-LOCAL.md](deploy/README-LOCAL.md).
- Standard local verification:

```powershell
cd deploy
docker compose --env-file ../.env.local -f docker-compose.yml -f docker-compose.local.yml up --build -d
docker compose --env-file ../.env.local -f docker-compose.yml -f docker-compose.local.yml ps
docker compose --env-file ../.env.local -f docker-compose.yml -f docker-compose.local.yml exec backend python -m compileall app alembic
docker compose --env-file ../.env.local -f docker-compose.yml -f docker-compose.local.yml exec frontend nginx -t
```

## Notes
- This repo does not terminate TLS.
- Server deployment assumes sibling `root-proxy` is the only public entrypoint.
- Database schema is managed by Alembic migrations at backend startup.
- `INITIALIZATION_EMAIL` seeds one hidden `admin` user at startup. It is allowed by env, is not inserted into `user_whitelist`, and is not shown in normal admin whitelist/user APIs.
- Runtime whitelist changes persist in PostgreSQL. Deleting a whitelist entry through the admin API also deletes the matching user row.
- Deleting a user cascades to sessions and organization memberships.
- Deleting a session directly is not an operational path; let cleanup or user deletion handle it.
