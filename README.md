# Evaluation Protocol

Internal HR evaluation stack behind sibling `root-proxy`.

## Runtime

- Public entrypoint: `root-proxy`
- Public host: `evaluation.example.com`
- Edge upstream: `evaluation-protocol:8080` on external Docker network `edge-net`
- Frontend: Vite + React packaged behind NGINX
- Backend: FastAPI
- State: PostgreSQL for users, sessions, OAuth transactions, DB whitelist, organization tree data, evaluation cycles, assignments, answers, and scores
- Auth: backend-owned Microsoft OAuth redirect flow with `HttpOnly` session cookie auth

## Active Scope

- Microsoft OAuth login through backend-owned transaction state
- env initialization account and DB whitelist enforcement before user creation
- `user/admin` system role
- user whitelist administration
- organization tree administration under seeded company node
- multiple leaders and multi-department membership support through organization memberships
- peer review team management
- self, peer, and manager-detail evaluation workflows
- hourly cleanup for expired/revoked sessions and stale/completed OAuth transactions

## In Repo

- `frontend/`: Vite + React frontend packaged behind NGINX
- `backend/`: FastAPI backend and Alembic migrations
- `deploy/`: container deployment files for this stack
- `docs/`: architecture, database operations, maintenance, and working notes

## Runtime Entry Points

- All runtime, deploy, and verification flows are defined from `deploy/`.
- Shared base compose: `deploy/docker-compose.yml`
- Server runtime: `deploy/docker-compose.server.yml` with repo-root `.env`
- Local runtime: `deploy/docker-compose.local.yml` with repo-root `.env.local`
- The server and local flows differ only by the compose override and env file.

## Setup Flow

From a fresh checkout:

```bash
git clone <repo-url> ~/evaluation-protocol
cd ~/evaluation-protocol/deploy
sh deploy.sh
```

Then choose one runtime guide:

- Server: `deploy/README-SERVER.md`
- Local: `deploy/README-LOCAL.md`

Before starting containers, replace every `$your-...` placeholder in the selected
env file.

## Required Server Values

For server deployment, `.env` must match sibling `root-proxy` routing:

```text
root-proxy route: evaluation.example.com -> evaluation-protocol:8080
EVALUATION_PROTOCOL_CONTAINER_NAME=evaluation-protocol
```

Set these environment values before server startup:

- PostgreSQL database, user, and password
- Microsoft Entra tenant, client ID, and client secret
- Microsoft redirect URI in Entra: `https://evaluation.example.com/api/v1/auth/callback/microsoft`
- `INITIALIZATION_EMAIL`: the first bootstrap admin account
- `COMPANY_EMAIL_DOMAIN`: the allowed company email domain for imported users
- `SESSION_COOKIE_SECURE=true`

## Local IDE Setup

This section is only for editor support and local code navigation. Runtime,
verification, and tests are Docker-only.

Do not install local PostgreSQL. Use the Compose stack from `deploy/`.

Keep these disposable local helper artifacts only when you want fast IDE
resolution:

- `frontend/node_modules`: local frontend dependency tree for TypeScript, Vite, and `npm` checks
- `frontend/dist`: disposable output generated by `npm run build`
- `backend/.venv`: lightweight Python interpreter and packages for IDE resolution and compile checks

If those artifacts are missing and you intentionally want local IDE indexing,
recreate them with:

```powershell
cd backend
py -3.13 -m venv .venv
.venv\Scripts\python -m pip install --upgrade pip
.venv\Scripts\python -m pip install -r requirements.txt -e .
.venv\Scripts\python -m compileall app
cd ..\frontend
npm install
npm run typecheck
npm run build
```

Do not use local dev servers, local PostgreSQL, or ad hoc runtime commands as
validation gates. Use Docker Compose from `deploy/`.

## Notes

- This repo does not terminate TLS.
- Server deployment assumes sibling `root-proxy` is the only public entrypoint.
- Database schema is managed by Alembic migrations at backend startup.
- Compose uses required env interpolation, so missing env values fail before container startup.
- `INITIALIZATION_EMAIL` seeds one hidden `admin` user at startup. It is allowed by env, is not inserted into `user_whitelist`, and is not shown in normal admin whitelist/user APIs.
- Runtime whitelist changes persist in PostgreSQL. Deleting a whitelist entry through the admin API also deletes the matching user row.
- Deleting a user cascades to sessions and organization memberships.
